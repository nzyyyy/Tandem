# Core 开发与验收

日期：2026-11-16。依据产品基线 §9.5、§10.1–10.3，补齐手动备份与恢复，并回归四条 Core 用户旅程。沿用现有 SQLite Schema 4、模型协议和 pi SDK；没有新增依赖。应用构建号为 10。

## 交付与使用

“模型设置”底部新增“备份与恢复”。配置有未保存编辑时，先保存或放弃修改。导出和选择备份仅在用户点击时打开系统文件选择器；恢复预览和确认在页面内完成。

导出为普通 UTF-8 JSON 文件，格式标识 `tandem-backup`、格式版本 1。包记录应用版本、创建时间、数据库及配置 Schema 版本，以及每个文件的路径、类型、字节数、SHA-256 和 Base64 内容；不加密、不压缩，不要求密码。限制总数据 128 MiB、4096 个文件、路径最多 16 层、包最多 192 MiB。编码前后都校验大小；读取使用有界文件描述符，不跟随文件符号链接。

数据库使用 `VACUUM INTO` 生成包含已提交 WAL 的一致性快照，校验完整性与外键。快照及配置读取、受管附件收集在 Node 同一同步维护窗口完成，不允许业务回调穿插写入；配置在发布前复核 revision。配置只导出经过校验、清空 `key` 字段的副本，不修改本机 Key。目录权限的文件描述符仅在 Swift 内存中，不进备份；数据库中的目录身份是不可授权的资源引用。外部授权目录不复制。当前 Evidence、报告和 Snapshot 均在 SQLite；`attachments/` 若存在则按文件清单完整保存，不包含迁移副本、恢复保护副本或其他数据目录内容。

导出位置必须在应用数据目录之外，拒绝目录别名绕过，不覆盖已有文件。完整写入、同步及回读校验后才用同目录硬链接原子发布；文件系统不支持该操作时导出失败。失败会清理暂存输出，文件权限 0600。SQLite 官方说明确认 `VACUUM INTO` 是生成一致性备份的支持方式，见 [SQLite VACUUM](https://sqlite.org/lang_vacuum.html)。

## 恢复与故障保护

1. 选择文件后在私有暂存目录校验格式、版本、文件清单、规范 Base64、大小、校验值、路径、数据库结构、完整性与外键，以及无 Key 的模型配置。拒绝重复路径、路径越界、链接类型、不支持的文件结构、额外触发器/视图、未知虚拟表及未来版本；不执行包内脚本或加载扩展。支持的旧 Schema 只在副本上迁移，再对照当前结构校验。预览展示备份时间、应用版本及各类数据数量，令牌 30 分钟有效，取消或新预览使旧令牌失效。
2. 用户点击“确认替换并恢复”后，阻止新派发和业务写入，取消并等待现有模型/工具工作退出；迟到输出不会写入恢复后的数据库。暂存失败不替换当前数据。
3. 合并本机当前尚未解除的遗忘标记，重新清理旧包中的匹配记忆、快照、检查点、派生回答与模型创建的任务正文。原用户证据保留，重新提取仍受标记约束；备份中的已解除状态不能解除当前有效标记。
4. 恢复保留预算消耗与耗尽原因。待处理工作保持中断或暂停，Outbox 不自动派发。旧审批保留为失效记录，不可消费；尚未完成的目录申请变为不可复用审批结果。目录授权全部不可用，Swift 同时撤销内存授权。无法核实的内部写入工具调用标为 `unknown`，继续前明确阻塞，不重放调用。
5. 暂存数据重新构建检索索引，完成完整性校验、WAL 检查点及文件同步。关闭当前数据库后，将整个原数据目录改名保存到相邻的 `.protection-…` 目录，包含受管附件和完整本机配置；目录权限 0700，Key 配置仍为 0600。再将已验证暂存目录整体切换到原位置，不逐文件覆盖活跃目录。
6. 私有恢复日志记录两次目录改名；启动时先处理日志。未提交的切换回滚到原目录，已切换的失败副本另存为 `.failed-…`。恢复成功后显示保护副本路径并切换数据代次，所有窗口清空旧历史缓存后重新加载，模型配置干净的窗口重新读取配置；未保存编辑继续受原有冲突保护。

恢复只恢复数据；重新填写模型 Key、主动选择目录后，才能手动继续需要这些资源的工作。保护副本保存原本机 Key，用于本机故障恢复，不作为可分享的脱敏导出。已经导出的旧备份不会随遗忘自动改写；恢复遗忘保护依赖本机仍可获得的标记。保护副本、迁移副本及 SQLite WAL 不承诺物理擦除。
